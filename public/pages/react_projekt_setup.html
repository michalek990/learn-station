Start
Inicjalizacja projektu — Vite + React + TypeScript
Jeden szablon startowy który daje Ci Vite, React 18 i TypeScript razem. Następnie instalujesz kolejne narzędzia osobno. Kolejność ma znaczenie.
Terminal — utwórz projekt
# Utwórz projekt Vite z szablonem React + TypeScript
npm create vite@latest nazwa-projektu -- --template react-ts

# Wejdź do folderu i zainstaluj zależności
cd nazwa-projektu
npm install

# Uruchom serwer deweloperski
npm run dev
# → otwórz http://localhost:5173
package.json — co ląduje po starcie
{
  "scripts": {
    "dev":   "vite",           // serwer deweloperski
    "build": "vite build",    // buduje produkcję
    "preview":"vite preview"  // podgląd buildu
  },
  "dependencies": {
    "react":     "^18.x",
    "react-dom": "^18.x"
  },
  "devDependencies": {
    "vite":            "^5.x",
    "typescript":      "^5.x",
    "@vitejs/plugin-react": "^4.x"
  }
}
⚡ Dlaczego Vite, nie Create React App?

Vite jest 10-20x szybszy od CRA przy starcie dev serwera. CRA używa Webpack który musi skompilować cały projekt przy starcie. Vite używa natywnych ES Modules — serwuje pliki bezpośrednio, bez kompilacji.

Hot Module Replacement (HMR) w Vite działa w <50ms. W CRA często kilka sekund.

CRA jest oficjalnie przestarzały od 2023 roku. Vite = nowy standard.

TS Dlaczego TypeScript?

TypeScript dodaje typy do JavaScript. Zamiast dowiedzieć się o błędzie gdy użytkownik kliknie przycisk — dowiadujesz się w edytorze gdy piszesz kod.

const sum = (a: number, b: number) => a + b

Jeśli przypadkowo wywołasz sum("5", 3) — edytor podkreśli błąd natychmiast, nie w runtime. Autocomplete, refaktoring, dokumentacja — to wszystko działa lepiej z TS.

02 / 04
Jakość kodu
ESLint + Prettier — automatyczne dbanie o jakość kodu
ESLint wyłapuje błędy i złe praktyki. Prettier formatuje kod (wcięcia, cudzysłowy, przecinki). Razem dbają żeby kod był spójny niezależnie od tego ile osób w zespole nad nim pracuje.
Instalacja ESLint + Prettier
# ESLint z pluginami dla React i TypeScript
npm install -D eslint \
  @eslint/js \
  eslint-plugin-react \
  eslint-plugin-react-hooks \
  @typescript-eslint/eslint-plugin \
  @typescript-eslint/parser \
  eslint-plugin-jsx-a11y

# Prettier + integracja z ESLint
npm install -D prettier \
  eslint-config-prettier \
  eslint-plugin-prettier

# Dodaj skrypty do package.json:
"lint":       "eslint src --ext .ts,.tsx"
"lint:fix":   "eslint src --ext .ts,.tsx --fix"
"format":     "prettier --write src"
.prettierrc — konfiguracja formatowania
{
  "semi": true,           // średniki na końcu linii
  "singleQuote": true,    // ' zamiast "
  "tabWidth": 2,          // 2 spacje wcięcia
  "trailingComma": "es5", // przecinek po ostatnim elemencie
  "printWidth": 100,      // max 100 znaków w linii
  "arrowParens": "always" // (x) => zamiast x =>
}
◈ ESLint — co sprawdza

✅ Brakujące key w listach React

✅ Użycie zmiennej przed deklaracją

✅ Reguły hooków React (eslint-plugin-react-hooks)

✅ Niedostępne elementy (jsx-a11y — brakujące alt, aria-label)

✅ Błędy TypeScript których kompilator może nie złapać

Efekt: npm run lint — wyświetla listę problemów. npm run lint:fix — naprawia co może automatycznie.

✦ Prettier — po co jak jest ESLint?

ESLint sprawdza jakość kodu. Prettier dba o formatowanie — wcięcia, odstępy, długość linii. Robią różne rzeczy.

Prettier formatuje automatycznie przy zapisie pliku (plugin VSCode) lub przy commicie (Husky). Koniec dyskusji w zespole o stylu — Prettier decyduje.

💡 VSCode — formatuj przy zapisie Zainstaluj rozszerzenia: ESLint i Prettier. W ustawieniach VSCode: "editor.formatOnSave": true i "editor.defaultFormatter": "esbenp.prettier-vscode". Kod formatuje się sam przy każdym Ctrl+S.
03 / 04
Testowanie
Vitest + Testing Library — testy jednostkowe i komponentów
Vitest to nowoczesny test runner zintegrowany z Vite — używa tej samej konfiguracji, jest szybki jak błyskawica. Testing Library pozwala testować komponenty React tak jak użytkownik — przez klikanie i sprawdzanie co widać na ekranie.
Instalacja Vitest + Testing Library
# Vitest + środowisko jsdom (symuluje przeglądarkę)
npm install -D vitest \
  @vitest/ui \
  jsdom \
  @testing-library/react \
  @testing-library/jest-dom \
  @testing-library/user-event

# Skrypty w package.json:
"test":    "vitest"
"test:ui": "vitest --ui"   // ładny panel w przeglądarce
"coverage":"vitest --coverage"
vitest.config.ts + przykładowy test
// vitest.config.ts
import { defineConfig } from "vitest/config";
export default defineConfig({
  test: {
    environment: "jsdom",   // symulacja przeglądarki
    globals: true,           // describe/it/expect bez importu
    setupFiles: "./src/setupTests.ts"
  }
});

// Przykładowy test — Button.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { Button } from "./Button";

it("wywołuje onClick po kliknięciu", async () => {
  const onClick = vi.fn(); // mock funkcji
  render(<Button onClick={onClick}>Kliknij</Button>);

  await userEvent.click(screen.getByRole("button"));

  expect(onClick).toHaveBeenCalledOnce();
});
✓ Testing Library — filozofia

"Test jak użytkownik, nie jak developer."

Zamiast sprawdzać wewnętrzny stan komponentu, sprawdzasz co widzi użytkownik:

screen.getByRole("button", { name: /wyślij/i })
screen.getByLabelText("Email")
screen.getByText("Zapisano!")

Testy pisane w ten sposób są odporne na refaktoring — zmiana implementacji nie psuje testów, bo użytkownik nadal widzi to samo.

04 / 04
Git Hooks
Commitlint + Husky — porządek w historii Git
Commitlint pilnuje żeby każdy commit miał sensowną wiadomość w formacie feat: dodaj przycisk. Husky uruchamia ESLint i testy automatycznie zanim zacommitujesz. Nie możesz zacommitować zepsutego kodu.
Instalacja Husky + Commitlint
# Husky — uruchamia skrypty przy git hooks
npm install -D husky
npx husky init

# Commitlint — sprawdza format wiadomości commita
npm install -D @commitlint/cli \
              @commitlint/config-conventional

# Utwórz commitlint.config.cjs:
module.exports = {
  extends: ["@commitlint/config-conventional"]
};

# Dodaj hook commit-msg:
echo "npx commitlint --edit \$1" > .husky/commit-msg

# Dodaj hook pre-commit (lint + testy):
echo "npm run lint && npm test -- --run" > .husky/pre-commit
📝 Format commitów — Conventional Commits

Format: typ(zakres): opis

feat: nowa funkcjonalność

fix: naprawa błędu

refactor: refaktoring kodu

docs: zmiany dokumentacji

style: formatowanie, bez logiki

test: dodawanie testów

chore: utrzymanie projektu

✅ feat(auth): dodaj logowanie przez Google

❌ zmiany — commitlint odrzuci!

05 / 04
Mapa projektu
Co to są te wszystkie pliki w root projektu?
Po zainstalowaniu wszystkich narzędzi w głównym folderze ląduje kilkanaście plików konfiguracyjnych. Każdy ma jedno zadanie. Oto co każdy robi.
⚡ Vite & TypeScript
vite.config.ts
Konfiguracja Vite. Ustawiasz pluginy (react), alias ścieżek (@/ zamiast ../../), port serwera, proxy do API.
tsconfig.json
Konfiguracja TypeScript. Jak rygorystycznie TS sprawdza kod, jakie flagi są włączone, które pliki kompiluje.
tsconfig.node.json
Oddzielna konfiguracja TS dla plików Node.js (np. vite.config.ts). Inne ustawienia niż dla kodu przeglądarki.
vitest.config.ts
Konfiguracja testów. Środowisko jsdom, setup files, coverage, globale (describe/it/expect).
postcss.config.js
PostCSS — procesor CSS. Potrzebny przez Tailwind CSS. Przetwarza CSS przed dostarczeniem do przeglądarki.
tailwind.config.js
Konfiguracja Tailwind CSS. Które pliki Tailwind ma skanować (content), własne kolory, fonty, rozszerzenia.
◈ Linting, Formatowanie & Git
.eslintrc.cjs
Konfiguracja ESLint. Które reguły są włączone, jakie pluginy, które pliki ignorować. .cjs bo projekt używa ES Modules.
.eslintignore
Co ESLint ma pomijać. Zazwyczaj: dist/, node_modules/, pliki generowane automatycznie.
.prettierrc
Konfiguracja Prettier. Styl formatowania: cudzysłowy, średniki, wcięcia, długość linii. Jeden plik — cały zespół formatuje tak samo.
.prettierignore
Co Prettier ma pomijać. Podobnie jak .eslintignore — pliki które nie powinny być formatowane (buildy, generowane pliki).
commitlint.config.cjs
Reguły dla wiadomości commitów. Zazwyczaj: extends: ["@commitlint/config-conventional"]. Jeden liner.
.gitignore
Co Git ma ignorować. node_modules/, dist/, .env (hasła!), pliki edytora. Vite generuje go automatycznie.
🔐 Zmienne środowiskowe & inne
.env.prod
Zmienne produkcyjne. URL API produkcyjnego, klucze serwisów (bez sekretów!). W Vite zmienne muszą zaczynać się od VITE_ żeby być dostępne w kodzie.
.env.test
Zmienne dla testów. Np. URL mock API, flagi feature. Ładowane automatycznie przez Vitest.
index.html
Jeden HTML dla całej aplikacji (SPA). Ma <div id="root"> gdzie React montuje aplikację. Vite wstrzykuje tu skrypty automatycznie.
Dockerfile
Konfiguracja kontenera Docker. Jak zbudować i uruchomić aplikację w izolowanym środowisku. Używany w CI/CD i deploymencie.
📦 Zarządzanie paczkami & CI
package.json
Serce projektu. Lista wszystkich zależności, skrypty npm (dev, build, test, lint). Tu dodajesz nowe biblioteki.
package-lock.json
Zamrożone wersje wszystkich paczek. Gwarantuje że każdy w zespole zainstaluje dokładnie te same wersje. Commituj do Git, nie edytuj ręcznie.
yarn.lock
To samo co package-lock.json, ale dla Yarn. Jeśli projekt używa Yarn zamiast npm — ten plik zamiast package-lock.
.npmrc
Konfiguracja npm. Np. prywatny rejestr paczek firmowych, token do autoryzacji, ustawienia proxy.
.gitlab-ci.yml
Pipeline CI/CD dla GitLab. Co robić automatycznie po każdym pushu: instaluj, lintuj, testuj, builduj, deployuj. Odpowiednik .github/workflows/ dla GitHub Actions.
.gitmodules
Git Submodules. Jeśli projekt zawiera inne repozytoria Git jako podmoduły (np. wspólna biblioteka komponentów). Rzadko spotykane w prostych projektach.
📋 Pozostałe
components.json
Konfiguracja shadcn/ui. Gdzie zapisywać komponenty, jaki styl, czy używać TypeScript, ścieżka do aliasów. Generowany przez npx shadcn@latest init.
README.md
Dokumentacja projektu. Jak uruchomić, jak zainstalować, jak wdrożyć. Pierwsza rzecz którą widać na GitHubie/GitLabie. Pisz to dla siebie za 6 miesięcy.
uiupdate.sh
Skrypt bash do aktualizacji komponentów UI. Prawdopodobnie skrypt który automatycznie aktualizuje komponenty shadcn/ui do nowych wersji jedną komendą.
⚠️ .env i sekrety Pliki .env z prawdziwymi hasłami i kluczami API nigdy nie trafiają do Gita. Dodaj je do .gitignore. W repo trzymasz tylko .env.example z pustymi wartościami jako szablon dla nowych developerów.
